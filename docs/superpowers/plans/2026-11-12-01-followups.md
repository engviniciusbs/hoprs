Plans 1 to 5 (foundation and transfer engine, SSH and SFTP, FTP and FTPS, vault and FileZilla import, the iced app) are done; Plan 6 (terminal, remote editing, palette, log, perf job) is on branch `plan-6-terminal-polish`. # Plan 1

## Fix before Plan 5 (UI)

- **Resolved in Plan 5.** **Event resync.** Expanding a large folder emits one `Added` event per entry into a 1024-slot broadcast channel. After `Lagged`, `snapshot()` has no sequence number, so a stale buffered `StateChanged` can overwrite newer state. Add sequence numbers to events and snapshots, or batch `Added`. Document "on `Lagged`, re-snapshot". (`Event { seq, kind }` and `snapshot_with_seq`; the queue drops stale events and re-snapshots on `Lagged`.)
- **Resolved in Plan 5.** **`TransferEngine::start` cannot report a failed recovery.** A corrupt queue then shows as an empty queue with no signal. Make `start` fallible or emit a startup error event. (`start` returns `Result`. The app falls back to an in-memory queue, logs it, and surfaces it: `Backend::open` keeps the error, `BackendApi::queue_error` exposes it, and the queue panel's error bar says "Transfer queue unavailable: … Transfers this session won't survive a restart." `crates/hoprs-app/src/backend/mod.rs` `start_engine`.)
- **Resolved in Plan 5.** **No clear-finished API.** The actor's `items` map only grows, which conflicts with the idle-memory target in spec §9. Expose `QueueStore::clear_finished` through the engine and prune the actor's maps. (`TransferEngine::clear_finished`.)
- **Resolved in Plan 5.** **No final `Progress` event when a transfer completes or fails.** (`finish_progress` before the closing `StateChanged`.)
- **`pause` then an immediate `resume` on an item that holds a worker slot returns `Conflict`.** Still open after Plan 5.
- **An extra `StateChanged(Active)` is emitted when an already-finished folder is reactivated and has nothing pending.** Still open after Plan 5.
- **"N items failed" grammar.** The text is fixed by the plan's test. Move it to i18n. Still open after Plan 5.
- **A `resolve` choice is lost if the item is paused while still Queued.** The destination is untouched, so with `Ask` the user is asked again. Still open after Plan 5.

## Fix before or during Plan 2 (SSH/SFTP)

- **A listing entry with an invalid name fails the whole folder.** Still open after Plan 2. Revisit for hostile servers; it could mark only that entry Failed.

## Hygiene (any time)

- **`state_detail` has three meanings: skip reason, pause origin and override.** Move them into separate columns in a future migration.
- **The dispatch stores only a `Some` override.** Always writing `set_next_policy(id, override)` would remove the dependency on the Queued-row invariant.
- **Test gaps** in `RemotePath` edge cases, io error mapping, MemFs permission and rename refusals, `decide()` with both mtimes `None`, store corner cases, and `copy_file` resume at `offset == size` and `offset > size`.
- **Timing-sensitive tests** (300 ms windows, and `large_tree_is_lazy` panicking on a lagged receiver) may be flaky on the Windows CI runner. Watch them.
- **Windows-specific.** `LocalFs::set_modified` on directories, reserved names (`NUL`, `CON`), and lossy conversion of non-UTF-8 names in `list`.
- **Case-insensitive duplicate names on download (Windows).** Duplicate-name detection in a listing is an exact match, so `A.txt` and `a.txt` from a case-sensitive server both become children and write the same local file on a case-insensitive file system (NTFS, default macOS). Compare names case-insensitively when the local side is case-insensitive.

# Plan 2

## Before Plan 5 (UI)

- **Resolved in Plan 5.** **`Unknown` cannot say that other key types are known.** A host known by its ed25519 key that presents only an RSA key is a plain "new host" prompt on a first connect (reconnects are pinned to the first key). `HostKeyStatus::Unknown` and `Prompter::confirm_host_key` should report "other key types are known for this host" so the UI can warn. (`other_key_types` reaches the dialog's warning.)
- **`learn` writes plain host names.** Ubuntu ships `HashKnownHosts yes`; write hashed entries (`|1|salt|hash`) when the user's config asks for it.
- **`write_atomic` replaces a symlinked `known_hosts`** with a regular file, and does not fsync the directory. A temp-name collision between two writers and a concurrent `learn` being lost are possible too.
- **Resolved in Plan 5.** **`remove` deletes whole wildcard or multi-host lines** (as `ssh-keygen -R` does). The UI must warn before removing a line that covers other hosts. (the in-place confirmation names the lines that cover other hosts.)
- **Resolved in Plan 5.** **Concurrent connects to the same unknown host both prompt and both append.** Serialize prompts per host. (the app's `PromptBroker` serializes host key and certificate prompts per `host:port` and waiters reuse the answer; checked live with three SSH sites on one host.)
- **Resolved in Plan 5.** **Session states for the UI.** `Connecting` is never observable (connect only returns once connected); a failed first connect leaves no session to `reconnect_now`; there is no "waiting for user" state while a reconnect attempt is prompting; a prompted (not saved) password is asked again on every reconnect. (`Connecting` and `WaitingForUser` are published, a prompted password is reused on reconnect, and a failed first connect has "Close and reconnect".)

# Plan 3

## Before Plan 5 (UI)

- **Resolved in Plan 5.** **suppaftp logs `PASS <password>` at trace level.** It logs every command it sends through the `log` crate, the password included. Any logger the app installs must cap the `suppaftp` target below trace (for example `suppaftp=debug`), or use suppaftp's `no-log` feature. The login call in `crates/hoprs-remote/src/ftp/session.rs` carries the same warning. (`crates/hoprs-app/src/main.rs` `log_filter`: by default `suppaftp` logs at warn (`info,suppaftp=warn`, also added to a `RUST_LOG` that does not set it); an explicit `RUST_LOG` that would let it reach trace is capped to debug.)
- **Resolved in Plan 5.** **The certificate prompt does not say why the certificate was rejected.** `CertProblem` is only `Untrusted` or `Changed`; an expired certificate, a wrong name and an unknown CA all look alike. The reason is at hand where the verifier rejects the chain (`chain_error` in `crates/hoprs-remote/src/ftp/tls.rs`, around line 137): carry it in `CertProblem` so the prompt can say "expired", "wrong name" or "unknown authority". (`CertProblem` carries the reason; the dialog shows it.)
- **Resolved in Plan 5.** **Certificate prompts are not serialized per `host:port`.** Several connections opening at once (the control connection and transfer connections, or two sites on the same server) can each ask about the same certificate and each store a pin. Serialize prompts per `host:port` and let the waiting ones reuse the answer (the SSH side has the same item for host keys). (`PromptBroker`, as for host keys.)
- **Resolved in Plan 5.** **The site watcher owns the connection and is never unregistered.** `spawn_site_watcher` holds an `Arc<dyn Connection>` (the owner of the state channel it waits on), so the watcher keeps the connection alive and only ends when the engine stops; there is no `unregister_site`. Plan 5 must abort the returned handle when a site is closed, or the watcher should hold a `Weak` and end when the last real owner drops. (`SessionManager` aborts the watcher when the site closes, `crates/hoprs-app/src/backend/sessions.rs`.)
- **Resolved in Plan 5.** **A stale pin stays in the profile** (ruling R5): a certificate that chains to a trusted root with the right name is accepted even when a different pin exists, and the old pin is never cleared. Plan 4 added `Vault::clear_ftps_pin`; the app (Plan 5) must call it when it sees that case. (`FtpPrompter::pin_superseded` lets the app call `Vault::clear_ftps_pin`.)
- **Resolved in Plan 5.** **Cancelling an FTP control command causes a visible reconnection.** A command dropped before its reply leaves the control connection in an unknown state, so the session replaces it. Navigation the UI cancels (leaving a folder while it lists) would flicker the connection state; the UI must not cancel these futures, or the session needs a quiet drain/replace. (listings carry a request id; a stale one finishes and is ignored, never cancelled.)

## Before perf/bench work

- **Resolved in Plan 6 (Task 10).** **Per-file metadata runs on the control connection, one command at a time.** The engine's `stat` of each file (`SIZE` + `STAT` + `MDTM`, about 3 round trips; 2 for a missing file since ruling R11) goes through the control connection's mutex, so with 4 workers on many small files the workers queue behind each other there. Run them on the worker's own `PooledConn` (already checked out for the transfer), or use `MLST` when `FEAT` announces it (one command). Before claiming the spec §9 small-files target for FTP, add an FTP small-files bench and compare it with `lftp` (`mirror -R --parallel=4`). (`stat` and `MFMT` run on a fresh idle transfer connection when one is free, `FtpSession::with_any`; the bench is `crates/hoprs-transfer/benches/network.rs`, numbers in `docs/perf/README.md`.)
- **Resolved in Plan 6 (Task 10).** **Every pooled reuse sends a `NOOP` first.** `FtpSession::checkout` checks an idle transfer connection with a `NOOP` (it may have hit the server's idle timeout): one extra round trip per file. Skip it when the connection was used recently (well under the server's idle timeout), and handle a dead one by retrying the transfer command on a fresh connection. (No `NOOP` for a connection back in the pool for less than 2 s, `POOL_FRESH`; when such a fresh connection turns out dead on its first command, the command is retried once on a newly opened connection (`FtpSession::checkout_new`, `FtpSession::with_any`), so the loss never reaches the engine as a `Network` error.)
- **No adaptive pool limit for per-IP connection limits.** Servers often cap connections per IP (vsftpd `max_per_ip`, shared hosts at 2–4). Opening an extra transfer connection then fails with `421` or `530`, which fails that transfer. Treat such a refusal of an *extra* connection as "the limit is lower": drop one permit for the session (never below 1) and wait for a connection to come back instead of failing.
- A `LIST` slower than `command_timeout` (120 s) on a huge directory or slow link counts as a lost connection and reconnects (ruling R6).
- `with_control` bounds a whole command with `command_timeout`, data connection included. If a config sets `command_timeout` below `connect_timeout`, an unreachable data address times the command out first and is taken as a control loss (reconnect churn) instead of a data channel error. The defaults (120 s / 15 s) are fine; nothing validates the order.

## Logging (any plan that adds a logger)

- `system_roots` drops certificate load errors silently.
- Unparsed `LIST` lines are skipped silently when at least one line of the listing parses. Log them at debug. (A listing in which no line parses is a `Protocol` error since ruling R11.)

## FTP edges (later)

- Ruling R8: `SIZE` and `STOR` follow symlinks on the server, so `open_read`/`open_write` called directly on a symlink to a file read or write the file. `stat` does not follow them (ruling R10: `STAT <path>`), so the engine refuses such a destination before opening it. Writes to a FIFO are left to the server (vsftpd refuses them). `MLST`, when announced, could replace `SIZE` + `STAT` + `MDTM` with one command.
- A server that answers `213` to `SIZE` on a directory: `stat` then reads `STAT <path>`, which lists the directory's contents. A `.` line, several entries or another name fall back to the parent listing; only a `STAT` without `.` whose single child has the directory's own name would be mistaken for that child.
- A `STOR` refused over an existing read-only file maps to `Io` ("File name not allowed", `553`), not `Permission`: `explain_write` only relabels a refusal for a missing file in an existing directory.
- A `522` reply (TLS data connection refused, e.g. `require_ssl_reuse` without resumption) maps to `Protocol` with the reply in the detail. rustls' session cache satisfies vsftpd's `require_ssl_reuse=YES` (tested), so no special hint was added.
- When an upload's data connection fails only at `shutdown` (after every byte was written), suppaftp returns the socket error and drops the server's reply (even a `426`). `FtpFs` then sends a `NOOP`: if the control connection answers, the upload is reported as `Io` ("Upload refused by the server") without the server's reason. It fails safe.
- **The `MLSD` path never ran against a real server**: vsftpd has no `MLSD`, so it is only unit-tested. Add a `pure-ftpd` or `proftpd` service to `docker/compose.yml` and run the `FtpFs` contract tests against it too.
- **No MS-DOS `LIST` parser.** Since ruling R11 a listing in that format (IIS's default) is a `Protocol` error, "Cannot read the server's listing format", instead of an empty folder; IIS sites need `MLSD` (IIS announces it) or a DOS-format parser.
- Ruling R11 trade-off: `stat` of a path under a parent the server cannot search says `NotFound` (vsftpd's `STAT <path>` lists nothing there, as for a missing path), not `Permission`. Nothing is overwritten (the `STOR` that follows fails and is explained as `Permission`), but a download from there reports `NotFound`.
- **Resolved in Plan 6 (Task 5).** **A probe can be dropped while the control connection is busy.** `PooledConn::report` wakes the supervisor (`Notify`) to probe the control connection with a `NOOP`, but `keepalive` only `try_lock`s the control mutex: when a command (a big `LIST`) holds it, the probe is dropped, and a dead server is only noticed by that command's own timeout or the next keepalive. (`keepalive` now waits for the command, then sends the probe's `NOOP`; the periodic keepalive only if the connection is still idle.)
- A `LIST` line whose owner or group is named like a month can be misparsed as a date (rare).
- Children of a symlink to an unreadable directory report `NotFound` instead of `Permission` (documented).
- `stat` under a parent whose listing is a single line costs an extra `stat(parent)` round trip (rare).
- `FtpSession::checkout` does not watch the session state while it opens a connection or checks one with `NOOP`.

## Test gaps and hygiene

- No test that `open_control` sends `TYPE I` and `OPTS UTF8 ON`; `reply_parts` has no non-UTF-8 or multi-line unit test.
- No tests for the supervisor shutting down mid-backoff or for the `InFlight` cancel path.
- The site watcher tests use a `settle()` yield heuristic instead of a deterministic sync point.
- **Committed test keys.** The test keys and certificates in `docker/fixtures/ftps` (and the SSH test keys) may trip secret scanners (GitHub push protection, gitleaks); allowlist those paths before the repo goes public.

# Plan 1 code found during Plan 3

- **Resolved in Plan 5.** **`spawn_copy` races the cancel token.** The engine's `spawn_copy` checks the item's cancel token only between reads; a cancel (or pause) that arrives while a read or write is pending waits for that call to return. Plan 3's FTP data timeout bounds that wait at `data_timeout`, but the engine should `select!` the copy against the token so a cancel is immediate on every backend. (`select!` against the token with a 200 ms grace.)
- **The watcher's restore budget never decays while the connection stays up.** `MAX_GRACE_RESTORES` resets only on a new generation or a user resume. Three network failures hours apart use it up, and the fourth leaves the site paused. Consider resetting the count after a successful transfer.
- **R11 assumes that `STAT <empty dir>` lists something.** vsftpd lists `.` and `..`. A server that answers an empty 213 would make the public `stat` call an existing empty directory NotFound; `mkdir` recovers through `stat_exact`. Verify alongside the MLSD / pure-ftpd service.
- **Pausing or cancelling during a stalled FTP read waits up to `data_timeout` (120 s)**, no longer forever. The `spawn_copy` cancel-race follow-up makes it immediate.

## Correctness

- **Resume after a dropped stalled copy can leave a hole.** The dropped copy skips the deferred-write-error guard (`crates/hoprs-transfer/src/engine/worker.rs` ~221, `copy.rs` ~22).
- **A failed persist lets a cleared item come back.** The store and the actor's maps disagree, and the item resurrects as Paused. Related: a failed `start` has already committed the active→paused update.
- **`clear_finished` emits no event.** The app re-snapshots after it (ruling), which leaves a window of stale rows if another event lands in between.
- **FTP double prompts.** FTP checkout can call `ensure_password` and prompt outside an attempt (`crates/hoprs-remote/src/ftp/session.rs` ~367, ~749). Its `WaitingForUser` guard is per prompt, not counted like SSH's `in_flight` (~411).
- **A stale SSH `waiting_hook`** from an abandoned attempt can put `Connecting` back too early (`crates/hoprs-ssh/src/session.rs` ~97).
- **Reconnect resumes a site the user paused.** `resume_site` clears the user's pause (`crates/hoprs-app/src/backend/sessions.rs` ~441).
- **A reused Disconnected session keeps its old secrets** after the password is edited (`sessions.rs` ~238). Likewise an in-flight connect finishes on the old endpoint after an edit, and Retry before the old session closes may reuse it.
- **Close is no longer serialized with a later connect.** A tiny window can leave the new session paused (`sessions.rs` close/ready). The close order and the broker's finish window have no pinning tests.
- **FTP may report directory symlinks as directories**, so a recursive delete follows them (`crates/hoprs-app/src/backend/ops.rs` `delete_all`). There is also no extra guard against deleting the home folder.
- **Rename `stat`** adds a round trip and a TOCTOU window. On FTP it may cost a parent listing.
- **Any mouse button release ends a pane drag as a drop** (a right click during a left drag). `DragEnd` is not blocked while a dialog is open (`crates/hoprs-app/src/app.rs` `Message::DragEnd`).
- **A queue snapshot older than `last_seq`** leaves the queue in Resyncing until the next one (`crates/hoprs-app/src/app/queue.rs`).
- **`failed_endpoint` comes from the profile**, not the dialled config. A saved passphrase per site is applied to all default keys. `remove_entries` refuses when unrelated lines shifted.
- **An unreadable site entry on reload closes its tab as "gone".** Skip the ids in `snapshot.unreadable`. (Out-of-order `LoadProfiles` snapshots: resolved in the final review, requests carry an id and an older result is dropped.)
- **`process::exit` skips destructors** (buffered logs) and exits 0 on an abandoned shutdown. A Failed or TimedOut shutdown is not surfaced (`crates/hoprs-app/src/effects.rs` ~346).
- **Secrets are not zeroized everywhere.** Typed passwords are left in iced `text_input` copies, and cancelled or withdrawn dialog secrets are not zeroized (`crates/hoprs-app/src/app/dialogs.rs`).
- **After a host/port edit, queued items resume against the new endpoint** (`crates/hoprs-app/src/backend/sessions.rs` ~440-442 `resume_site`, `crates/hoprs-app/src/app.rs` `profiles_loaded`/`drop_moved_session`). The site id stays the same, so the next session's `register_site` serves the old items, and a `Resume` continuation can splice the new server's bytes onto a partial file from the old one (or the reverse). Suggested fix: don't auto-resume a moved site (keep its items paused and say why in the queue), or force `Overwrite` for its in-flight continuations.
- **A secret typed with "save" can still be stored for a tab closed while connecting** if the connect already finished in the backend: `ready` takes the pending secrets under the sessions lock that `close` removes the session with, so a close that comes first always wins, but one that lands after `ready` took them (the `Connected` already on its way to the app) is too late. ## Correctness

- **Resolved in Plan 7.** The actor keeps one writer per destination (`writing`, keyed by `DestKey`: the site's remote path for an upload, the local path for a download): a queued item whose destination is being written waits in the queue while the site's other items go ahead, and starts when the owner frees its slot (done, paused, failed, cancelled or awaiting a decision); its conflict check then sees the owner's file (`tests/engine_destinations.rs`). **Two items can write the same destination at once** (Important; found in Task 10, pre-existing). Two queued items with the same destination file (two trees uploaded into one folder, both with `x`) can be prepared in parallel: both `stat`s see it missing, both copies write it, both fail "Size mismatch after transfer" and a mixed file is left. Serialize items per destination path in the actor (`crates/hoprs-transfer/src/engine/actor.rs`).
- **A flooding shell is closed, not slowed.** Once the app stops pulling (its feed holds 2 batches of 2 MiB in flight), the pump keeps reading into its output queue (256 items, up to 16 MiB) and then its pending buffer; past that buffer's 16 MiB cap (`MAX_PENDING_OUTPUT`) it marks the shell overflowed and closes it ("Output was too fast"). Stop reading (SSH window backpressure) instead (`crates/hoprs-ssh/src/shell.rs` `overflowed`, `crates/hoprs-app/src/backend/shells.rs`).
- **An unsubscribed shell pump parks on `reserve`.** After the pump finishes (overflow, `Eof` timeout, close), it only waits for room in the queue to deliver what it holds and `Closed`; nothing else wakes it (`stop` is only watched while reading). If nobody pulls the output and the receiver is not dropped (an output not taken from the backend's map yet, or a subscription that stopped polling), it holds up to ~32 MiB (16 MiB queued + 16 MiB pending) until `close_shell` (or the session's close) drops the receiver (`crates/hoprs-ssh/src/shell.rs` `pump`). Drop the pending output when `stop` fires after finishing, or bound the wait.
- **SFTP temp + rename loses owner, group and hard links** of an edited file (the new file is ours). `crates/hoprs-app/src/backend/edit.rs` ~1427; consider `fsetstat` of the old owner, or in-place writes when the owner differs.
- **A change during an edit's download is flagged as a remote change** (a safe false positive: the user is asked). The baseline stamp is taken before the download (`backend/edit.rs` `start_locked`). Taking it after the download was tried in the final review and reverted: it silently accepts a torn or just-overwritten download. Fix: compare the stamps before and after the download, and re-download (bounded) or keep the earlier stamp when they differ.
- **A closing session can be reused by a quick reopen.** `effects::close_session` now settles edits (waiting for an upload under way) before `backend.close`; meanwhile the session stays in the per-site lookup, so reopening the site (or reconnecting after an endpoint change) can pick up the closing session, which is then closed under the new tab. Take it out of the lookup (or mark it closing) before awaiting `finish_edits` (`crates/hoprs-app/src/backend/sessions.rs` `connect_site`).
- **A remote change with the same size in the same second goes unseen** before a re-upload (size + mtime only, `backend/edit.rs` `RemoteStamp`). Hash small files, or compare a second `stat` field.
- **Symlinked remote files can't be edited** ("Links can't be edited", `crates/hoprs-app/src/app/edit.rs` ~48), and edit names aren't checked against Windows reserved names.
- **Saving a recovered copy reads and hashes the edit file more than once** (`unsent`, then `preserve_unsent`/`keep` read it again and `preserve` hashes it again, `backend/edit.rs` ~870, ~1193, ~1240). Share one read and one hash.
- **Edit worker edges** (`backend/edit.rs`): one serial worker per session; `finish()` clearing `ending` may drop a debounced auto-upload; a sync cut by "keep" can leave the server's temp file; a late `Uploaded` for a closed edit; "may be incomplete" can be a false positive; `starting`/backoff maps never shrink.
- **Close flows** (`app/edit/close.rs`): repeated window close can't force quit during a busy workspace upload (Stop works); `unpark_form` may bring back an old form; a queued quit is silent after a failed settle; the `ExitWindow` chain has no test.
- **Resolved in Plan 6 (Task 8 close handling, final review).** **Edit retries after `close()` until `finish` depend on the state receiver.** Every close of a single session now ends its edits before closing it: `effects::close_session` runs `finish_edits` (which waits for an upload under way) and, for unsent edits, `keep_edits`, both of which abort the session's edit worker, and only then `close`; "Close and reconnect" (`effects::restart_site`) goes through it too (it closed the session behind the edits' back before). The worker also stops retrying once the session's state sender is gone (`closing_the_session_stops_the_retries`). Only the window's shutdown still closes the sessions before `end_all`, with `preserve_unsent` first, so nothing unsent is at risk in that short window.
- **Reconnect edges** (`crates/hoprs-app/src/app/reconnect.rs`): an idle terminal waiting from Restart gets no app reconnect when the transport gives up; `reconnect_for_held` may fire for closed-tab entries; a replayed id lingers on the transport-only path; the idle-check path can wait twice on a quick second loss; the extra quiet reconnect round per drop (ruling, Task 5).

# Plan 12

Folder compare (`hoprs_remote::compare`, the panel in `hoprs-app/src/ui/compare*.rs`).

Not built on purpose (non-goals of 1.2.0):

- **Delete one-sided files**, **mirror/sync** a folder, and **compare by content or checksum**: compare only looks at name, size and modification time and never deletes. Mirroring needs a deletion UX of its own; checksums need a hash per file over the wire (SFTP has no portable remote hash, FTP has `XCRC`/`XMD5` on some servers only).
- **Case-insensitive local file systems:** entries are matched case-sensitively, so `Readme.md` locally and `README.md` on the server show as one only-local and one only-remote row on macOS and Windows. Needs a per-side case-folding option.
- **FTP `LIST` time zone and year handling:** without `MLSD`, `LIST` times are read as the server shows them (no offset, minute precision, old files carry a date only). A server in another time zone than its listing says can show every file as newer or older by a few hours; the tolerance (60 s) does not cover it. Needs a per-site "server time offset" or `MDTM`/`MLST`-based probing. The Docker test only exercises a vsftpd listing in GMT (its default); servers with `use_localtime=YES` or non-GMT listings are untested.

Deferred minors (found in review, left on purpose):

- **Uploaded folders are not remembered as synced:** the files inside a folder the panel uploaded or downloaded are not added to the tab's synced memory, so on a server that cannot set mtimes they can still read as newer.

- **Closing one of several tabs that share an SSH session aborts the run:** it drops an SFTP readdir; a cooperative stop would do.

## Tools

- **`transfer_status` forgets a transfer** once it is cleared from the queue (and when its site is no longer open to agents).
- **On Windows the local side reaches only the current drive** (`LocalFs::new("/")`): a path on another drive, a UNC path and a relative path are refused with a sentence that says so.
- **`read_file` refuses a file whose last path component is a symbolic link:** `RemoteFs` has no `readlink` or `realpath`, so the target cannot be followed. A `readlink` operation on `RemoteFs` would lift it.
- **Check-then-act gaps:** `write_file` with `overwrite: false` and `rename` check that the target is absent and then act; another writer can slip in between. An exclusive create and a no-replace rename on `RemoteFs` would close them on SFTP.
- **The recursive `delete` walk has no depth, count or time limit,** and follows a folder swapped for a link in the middle of the walk. On some FTP servers a link to a folder is listed as a folder, so a recursive delete goes into it (the description says so).
- **The home and start folders are not specially protected** from `delete` (an agent at the "Allow everything" level can already do it with `run_command` on an SSH site). Only `/` is refused.
- **A timed-out command may keep running on the server:** hoprs sends a best-effort KILL; the answer says `timed_out` and that it may still run.
- **The tool schemas carry no `default` keywords** (the defaults are only in the descriptions).
- **The descriptions of `download` and `upload` do not mention links, the local parent folder or a paused transfer;** and no test runs the transfer tools at the real levels (the access matrix uses the fake host).

## Protected local paths

- **Time of check versus time of use.** The guard checks an agent item's local path before any file is touched, but between the check and the engine's `open` a directory on the path could be swapped for a link into a protected place, and the open would follow it. Closing it needs the engine to open relative to a checked directory handle (upload: open, then compare the identity; download: a temporary file in a re-checked directory, then rename).
- **The guard reuses its resolved roots for about two seconds within a batch.** A root newly replaced by a link, or a new hard link or bind mount to a root, is not seen in that window (the plain path rule still applies). A changed key-file list always re-prepares.
- **A pre-existing hard link to a non-root file inside a protected directory** is not recognised (Windows compares paths only; Unix compares device and inode for the roots). Equally, the target of a link that sits inside `~/.ssh` (a dotfiles setup: `~/.ssh/config` linked to `~/dotfiles/ssh/config`) is unprotected at its own path unless a site names it.
- **The folder rule now also covers the program:** a folder transfer onto the folder that holds a user-owned hoprs executable is refused (a portable `hoprs.exe` on the Desktop makes a folder transfer onto the Desktop itself fail), as it already is for the home folder because of `~/.ssh`.
- **No test pins the transfer guard for a refused folder, a retried item and a restored item.** The code has one dispatch path for all three, but the guard is the security core and deserves the pin.
- **macOS has a second path to the home directory** (`/System/Volumes/Data/Users/…`). The code compares file identities to catch it; it was reasoned in the code and never ran on a Mac (QA row).

## Sessions and prompts

- **A paused or queued agent transfer keeps an agent-only session open indefinitely:** the reaper never closes a site with an unfinished transfer (closing it would pause the site's queue).
- **Two waiters on one connect:** the first one's two-minute limit closes the agent-only session under the second. Calls on one unconnected site share one attempt since the fix round; check whether the second waiter's limit should be counted from its own start.
- **A session an agent uses that a tab closes:** the next agent call connects again. If an abandoned tab connect takes a session over and then closes it, a kept agent dialog can lose its session.
- **The `dialogs.saving` window (`crates/hoprs-app/src/app/dialogs.rs`):** a password typed in an agent's dialog with "save" ticked is kept until the connect succeeds; if the session ends in that window the password is not saved. Found in review, not reproduced.
- **An agent-only session whose network dropped shows connected** (sidebar and `list_sites`) until the reaper or the next call finds out.
- **A dialog already open when a tab takes the session over keeps its "asked by an agent" line** (cosmetic).
- **A cancelled waiter's close sends no `Sites` event,** and the sidebar's "Connected (by an agent)" mark can stay up to 30 s after a taken-over session closed: remove the site from the agents' list when its last tab closes.
- **An agent's call on a tab's disconnected session answers "check that the server is up"** (the network sentence of a failed connect) rather than that the connection is down in hoprs and the user has to reconnect the tab.
- **After a site edit, the endpoint check can close a stale agent-only session while another call of the same site still runs on it:** `same_endpoint` (`crates/hoprs-app/src/agent/service.rs`) looks at running transfers and at an attempt under way, not at other running calls (the reaper does check them), so that call fails as if the connection dropped (an FTP write in place can be left half written). Fix: treat another running call like the busy case. No test covers the ordering.
- **Orderings reasoned but untested** in the endpoint check and the re-admission: a tab taking the session over between the check and the close; a reading call re-admitted at a lower level that still allows it.
- **A site edited while an unfinished transfer uses its agent-only session** (fix wave, beyond its brief): the session is not closed, since closing pauses the site's queue and the next connect would resume the transfer on the new server. Calls on the site are refused with their own sentence until the site's transfers have ended; a paused agent transfer keeps them refused until it is resumed or cancelled.

## Platforms

- **macOS app translocation:** an app run from Downloads or from the disk image can be given a temporary path that changes at each launch, so the command copied from Settings stops working. The README says to move hoprs to Applications first; consider detecting a translocated path (`/private/var/folders/…/AppTranslocation/`) and saying so in Settings.

## From the end-to-end run (2026-11-22)

- **The local `..` refusal** is worded differently from the remote one and does not name `local_path`.
- **The log line of a refused `write_file`** reads "wrote … (failed: already exists)" although nothing was written.
- **`agent.sock` stays on disk after hoprs is killed:** the relay answers "not reachable" and the next start replaces it (harmless); a clean-up on a signal would be tidier.
- **The status bar shows "Not connected" next to "Agent connected"** when no tab is open, which can read as a contradiction.
- **The app's own log goes to stdout with colour codes even into a file** (older than this plan).
- **Make the end-to-end run repeatable:** a script (a container with a virtual display, the Docker sshd, a scripted MCP client) in the repository; today it lives outside it.
