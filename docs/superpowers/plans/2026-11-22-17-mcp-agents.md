# Plan 17: MCP server for agents (1.6.0) — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `hoprs mcp` lets a coding agent (Claude Code or any MCP client) list, read, write, transfer and delete files and run SSH commands on the saved sites the user opened to agents, at the level set per site, through the open hoprs window, which keeps the credentials and shows what the agent does.

**Architecture:** Two halves of one executable. `hoprs mcp` (the relay, `agent/relay.rs`) speaks MCP over stdio with the official Rust SDK and forwards each tool call, as one JSON line, over a local channel (a Unix socket beside the instance lock, a named pipe on Windows) to the running app. In the app, `agent/server.rs` accepts relays while the master switch is on and hands each call to `agent/service.rs`, which checks the switch and the site's level, then works through a narrow `AgentHost` trait over the backend's existing handles (vault, session manager, transfer engine, prompt broker). The UI reaches all of it only through two new `BackendApi` methods. `Site` gains the access level; `hoprs-transfer` gains the inherited policy, the origin of an item and a guard for agent items; `hoprs-ssh` gains the exec channel.

**Tech Stack:** Rust 1.99.1 (pinned), iced 0.14, tokio 1.54 (`net` added to `hoprs-app`; `io-std` comes with `rmcp`'s `transport-io`), `rmcp` 3.11 (`server` + `transport-io`, no default features), `serde_json` 1, `russh` 0.65, `rusqlite` 0.42, `windows-sys` 0.61, `libc` 0.2; site: Vite + React 19 + vitest.

**Spec:** `docs/superpowers/specs/2026-11-22-mcp-agents-design.md` (binding, including "Builder-check rulings", "Constraints", "Release" and "Left to the builder"). Read it with this plan.

**Starts from:** the finished branch of Plan 16 (`docs/superpowers/plans/2026-11-22-16-export-drive.md`). Rebase `mcp-agents` onto `export-drive` (onto `main` once Plan 16 is merged) before Task 1. What exists then and this plan builds on: `Form::Export` and `app/export.rs`; the **Export…** button left of Delete in `ui/site_form.rs`; `Vault::export_bytes(scope, …)` (the loop that clones each site is there, `Vault::export` calls it); the `BackendApi` methods `export_backup(scope, …)`, `drive_*`, `seal_export`, `save_sealed`; `AppSecretStore`; `Settings.google_drive` in `OPTIONAL_KEYS`; `Backend::with_app_secrets`; `site/src/Privacy.tsx` with `privacy.sections` in both dictionaries; `## 1.6.0 — unreleased` at the top of `CHANGELOG.md`; the Plan 16 lines in `CLAUDE.md`. ### Protocol facts (read on 2026-11-22; do not write protocol details from memory)

The current MCP revision is **2026-07-28**; the one before it is **2025-11-25**.

1. **Two eras** (https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning). *Legacy* (2025-11-25 and earlier): the client opens with `initialize`, the server answers, the client sends `notifications/initialized`. *Modern* (2026-07-28): **no handshake**; every request carries its version and capabilities in `params._meta`. A server may serve both ("dual-era"): an `initialize` request selects legacy semantics for the stdio process, a request with modern `_meta` is served statelessly. The changelog (https://modelcontextprotocol.io/specification/2026-07-28/changelog) removed `initialize`, protocol sessions, `ping` and `logging/setLevel` from the modern era and added `server/discover`.
2. **Claude Code speaks both** (https://code.claude.com/docs/en/mcp): its v1 client runtime is on the MCP TypeScript SDK 1.x (legacy handshake), its v2 runtime on SDK 2.0 "which adds MCP protocol revision 2026-07-28" and asks stdio servers "whether they support the newer revision". The relay must therefore be dual-era.
3. **stdio** (https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio): one JSON-RPC message per line, no embedded newlines; "The server MUST NOT write anything to its stdout that is not a valid MCP message"; logging goes to stderr; the server never writes requests; "Servers SHOULD exit promptly when their standard input is closed" (Claude Code on Windows closes stdin and ends the process tree 300 ms later). A dual-era client probes with `server/discover` first and falls back to `initialize` on any error that is not a recognised modern error.
4. **Modern request metadata** (https://modelcontextprotocol.io/specification/2026-07-28/basic/index#_meta): `params._meta` must hold `io.modelcontextprotocol/protocolVersion` (string) and `io.modelcontextprotocol/clientCapabilities` (object); `io.modelcontextprotocol/clientInfo` is optional. A request without a required key is rejected with `-32602`. A version the server does not serve is rejected with `{"code": -32022, "message": "Unsupported protocol version", "data": {"supported": ["2026-07-28", …], "requested": "…"}}`. Every modern result has `"resultType": "complete"`; servers should put `io.modelcontextprotocol/serverInfo` (`{name, version}`) in each result's `_meta`.
5. **`server/discover`** (https://modelcontextprotocol.io/specification/2026-07-28/server/discover), mandatory in the modern era: result `{"resultType":"complete","supportedVersions":[…],"capabilities":{"tools":{}},"instructions":"…","ttlMs":…,"cacheScope":"public"|"private","_meta":{…serverInfo…}}`.
6. **Legacy `initialize`** (https://modelcontextprotocol.io/specification/2025-11-25/basic/lifecycle): request `params` `{protocolVersion, capabilities, clientInfo}`; result `{protocolVersion, capabilities: {"tools": {}}, serverInfo: {name, version}, instructions?}`. The server answers the client's version if it supports it, else another version it supports. Legacy results have no `resultType`, `ttlMs` or `cacheScope`; `ping` exists and is answered with `{}`.
7. **Tools** (https://modelcontextprotocol.io/specification/2026-07-28/server/tools). `tools/list` result: `{"resultType":"complete","tools":[…],"ttlMs":<≥0>,"cacheScope":"public"}` (the two cache fields are required in the modern era, https://modelcontextprotocol.io/specification/2026-07-28/server/utilities/caching); the list must not vary per connection and should have a stable order. A tool: `name` (1–128 of `A-Za-z0-9_-.`), `title?`, `description`, `inputSchema` (JSON Schema 2020-12, root `"type":"object"`), `annotations?`. `tools/call` params: `{name, arguments}`; result `{"resultType":"complete","content":[{"type":"text","text":"…"}],"isError":false}`.
8. **Two kinds of error.** Unknown tool or a malformed request: a JSON-RPC error, `{"code": -32602, "message": "Unknown tool: <name>"}`. Everything the model can act on (bad argument values, no access, hoprs closed, a failed operation): a **tool execution error**, an ordinary result with `"isError": true` and the text in `content`.
9. **Annotations** (schema, https://modelcontextprotocol.io/specification/2026-07-28/schema#toolannotations): `title`, `readOnlyHint` (default false), `destructiveHint` (default true, meaningful only when not read-only), `idempotentHint` (default false), `openWorldHint` (default true). Claude Code runs calls of `readOnlyHint` tools in parallel and withholds one-tap approval for `destructiveHint` tools.
10. **Cancellation** (https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/cancellation): on stdio the client sends `{"jsonrpc":"2.0","method":"notifications/cancelled","params":{"requestId":…}}`; the server stops the work and sends no response for that id.
11. **Statelessness** (basic/index, "Statelessness"): state that spans calls "MUST be referenced by an explicit identifier the client passes on each request", and a server "SHOULD NOT require that a client reuse the same connection or process". Hence ruling 9 (transfer ids are not tied to a relay).
12. **Claude Code limits**: a text result over 50 000 characters is saved to a file instead of shown to the model, and the default cap is 25 000 tokens (`MAX_MCP_OUTPUT_TOKENS`). Hence the paging in ruling 7.
13. **`rmcp` 3.11.0** (https://github.com/modelcontextprotocol/rust-sdk; names read from the crate's source, the docs.rs page of the locked version wins if one differs): "implements the stable MCP 2026-07-28 specification" and stays compatible with 2025-11-25 and earlier, on one stdio process (it answers `server/discover`, `initialize`, pre-`initialize` `ping`, validates the modern `_meta`, fills `resultType` and the cache hints per era). `rmcp::handler::server::ServerHandler` methods used here: `fn get_info(&self) -> ServerConfig` (`ServerConfig::new(ServerCapabilities::builder().enable_tools().build()).with_server_info(Implementation::new(name, version)).with_instructions(text)`), `fn list_tools(&self, Option<PaginatedRequestParams>, RequestContext<RoleServer>) -> impl Future<Output = Result<ListToolsResult, ErrorData>>` (`ListToolsResult::with_all_items(tools)`), `fn get_tool(&self, name: &str) -> Option<Tool>`, `fn call_tool(&self, CallToolRequestParams { name, arguments, .. }, RequestContext<RoleServer>) -> impl Future<Output = Result<CallToolResponse, ErrorData>>` (`CallToolResult::success(vec![ContentBlock::text(s)]).into()`, `CallToolResult::error(vec![ContentBlock::text(s)]).into()`; `ErrorData::invalid_params(message, None)`); `context.ct` is cancelled when the client cancels the request. `Tool::new(name, description, Arc<serde_json::Map<String, Value>>).with_title(t).with_annotations(ToolAnnotations::new().read_only(b).destructive(b).idempotent(b).open_world(b))`. `rmcp::ServiceExt::serve(handler, transport)` takes any `(R, W)` of `AsyncRead` / `AsyncWrite` (`rmcp::transport::stdio()` for the real streams, `tokio::io::duplex` halves in tests) and returns a running service whose `.waiting()` ends when the input reaches end-of-file.

### Rulings this plan makes (left to the builder, or where the spec is silent)

1. **SDK: `rmcp`**, as the spec prefers, because its tree keeps the rules: `rmcp = { version = "3.11", default-features = false, features = ["server", "transport-io"] }` resolves to no TLS, no HTTP, no OpenSSL and no ring (checked with `cargo tree` on 2026-11-22), and because the protocol has two live eras whose wire details the SDK tracks (its changelog fixes one such detail per week). Cost: the ten packages of Global Constraints, four of them build-time macros; licences Apache-2.0 (`rmcp`, `unicode-general-category`), MIT (`schemars`), the rest MIT OR Apache-2.0. No `macros` feature: the tool list is a hand-written table (ruling 6). The relay supports every version the SDK knows (`ServerHandler::supported_protocol_versions` is not overridden). If a wire test of Task 13 cannot be satisfied through the SDK, stop and report: do not hand-write the transport without the author's word.
2. **Where the code lives.** `crates/hoprs-app/src/agent/`: `mod.rs` (limits, the agent-facing texts, `AgentEvent`), `proto.rs` (the channel's messages), `tools.rs` (the tool table), `paths.rs` (local paths and the protected ones), `host.rs` (`AgentHost`), `service.rs` (+ `service/files.rs`, `service/transfers.rs`), `channel.rs` (+ `channel/unix.rs`, `channel/windows.rs`), `server.rs`, `relay.rs`, `testing.rs` (`FakeHost`, test builds). The real host is `backend/agent.rs` (it needs the backend's private handles).
3. **`BackendApi` stays small.** It gains `set_agents_enabled` and `agent_events` only. The service is tested against `FakeHost` (an in-memory `AgentHost` over `MemFs`), not through `BackendApi`: the tools need a dozen operations the UI never calls, and `FakeBackend` keeps covering the UI.
4. **The channel's format:** one JSON object per line, UTF-8, at most 8 MiB a line. Relay first: `{"hoprs_agent":1,"version":"<CARGO_PKG_VERSION>"}`; app: `{"hello":"ok","version":"…"}` or `{"hello":"mismatch","version":"…"}` then close. A mismatch is a different `hoprs_agent` number **or** a different version string (relay and app are one binary: after an update the running window is the old one). Then relay → app `{"call":<id>,"tool":"…","args":{…}}` and `{"cancel":<id>}`; app → relay `{"reply":<id>,"ok":true,"blocks":["…"]}`, `{"reply":<id>,"ok":false,"error":"…"}`, and `{"bye":"off"}` / `{"bye":"quit"}` before the app closes the connection. Ids are the relay's, unique per connection, so calls overlap.
5. **Where the channel is.** Unix: `agent.sock` in the directory whose `instance.lock` this run holds (`run()` passes that directory down; without a lock there is no channel, logged once). The relay tries the directories of `instance_lock_paths()` in order and uses the first whose `agent.sock` exists. Windows: `\\.\pipe\hoprs-agent-<SID>`. Debug builds only: `HOPRS_AGENT_DIR=<dir>` replaces the directory for both halves (on Windows the pipe name gains `-` and the first 16 hex digits of the SHA-256 of the directory), so tests never meet the author's running hoprs.
6. **Tools:** thirteen, in this order in `tools/list`. Remote paths are absolute; local paths are absolute paths of this computer. Every tool but `list_sites` and `transfer_status` takes `site` (the id from `list_sites`).

   | Tool (title) | Arguments (`?` optional, default) | Level | read-only / destructive / idempotent / open-world |
   |---|---|---|---|
   | `list_sites` (List sites) | none | — | yes / – / – / no |
   | `list_directory` (List a folder) | `path`, `offset?` 0, `limit?` 1000 (1–5000) | Read | yes / – / – / yes |
   | `stat` (Describe a path) | `path` | Read | yes / – / – / yes |
   | `read_file` (Read a text file) | `path`, `offset?` 0, `length?` to the end | Read | yes / – / – / yes |
   | `download` (Download to this computer) | `remote_path`, `local_path`, `overwrite?` false | Read | no / yes / yes / yes |
   | `transfer_status` (Check a transfer) | `transfer` (integer) | — | yes / – / – / no |
   | `write_file` (Write a text file) | `path`, `content`, `overwrite?` false | All | no / yes / yes / yes |
   | `make_directory` (Create a folder) | `path` | All | no / no / yes / yes |
   | `rename` (Rename or move) | `from`, `to` | All | no / no / no / yes |
   | `set_permissions` (Change permissions) | `path`, `mode` (string, 3 or 4 octal digits) | All | no / no / yes / yes |
   | `upload` (Upload from this computer) | `local_path`, `remote_path`, `overwrite?` false | All | no / yes / yes / yes |
   | `delete` (Delete) | `path`, `recursive?` false | All | no / yes / yes / yes |
   | `run_command` (Run a command over SSH) | `command`, `timeout_seconds?` 60 (1–600) | All, SSH | no / yes / no / yes |

   Each `inputSchema` is `{"type":"object","properties":{…},"required":[…],"additionalProperties":false}` with a `description` per property. `local_path` / `remote_path` of a transfer are the path the item **will have**, not the folder to put it in (the description says so).
7. **Results** are text blocks (no `structuredContent`, no `outputSchema`: one shape for both eras). One compact JSON object per call, except: `read_file` answers a JSON header block `{"path","size","offset","length","next_offset","eof"}` and then the text as its own block; `run_command` answers a header `{"exit_code"|null,"signal"|null,"timed_out","stdout_truncated","stderr_truncated"}`, then a block `stdout:\n…` and a block `stderr:\n…` (each only when not empty). Shapes: `list_sites` → `{"sites":[{"id","name","protocol":"ssh"|"ftp"|"ftps-explicit"|"ftps-implicit","host","port","user","level":"read"|"all","connected","start_folder"|null}]}`; `list_directory` → `{"path","entries":[{"name","kind":"file"|"dir"|"symlink","size","modified"|null,"permissions"|null}],"offset","total","truncated"}` (entries sorted by name, `modified` RFC 3339 UTC, `permissions` four octal digits); `stat` → one entry with `"path"`; transfers → ruling 9; the others → `{"ok":true,…}` with what was done (`"bytes"`, `"deleted"`).
8. **Caps** (constants in `agent/mod.rs`, a `Limits` value in the service so tests shorten them): listing 1000 entries by default and 5000 at most per call, paged with `offset`; `read_file` and `write_file` 1 MiB (1 048 576 bytes) per call; `run_command` 256 KiB per stream, 60 s by default, 600 s at most; transfer wait 60 s; connection wait (prompts included) 120 s; idle close 10 minutes, checked every 30 s; at most 20 failed items named in a transfer summary; 8 calls in flight per relay (the next ones wait), 16 relays at once (a 17th is refused at the hello), one `run_command` at a time per site (the next waits; its time limit starts when it starts); hello within 5 s.
9. **Transfers.** `download` / `upload` enqueue one item with `EnqueueOptions { policy: Overwrite | Skip, origin: Agent }` and answer `{"transfer":<id>,"state":"done"|"skipped"|"failed"|"cancelled"|"running"|"paused","files_done","bytes_done","skipped","failed_count","failed":[{"path","reason"}]}`; `"running"` after 60 s. `transfer_status` answers the same for any transfer of origin Agent on a site the caller may still read (the id is the handle, not the connection: protocol fact 11); an unknown id, a user's transfer and a cleared one are the same error.
10. **`read_file`:** the range is `offset..offset+length` (to the end without `length`); a range over 1 MiB is an error naming the size and pointing to `offset`/`length` or `download`; bytes that are not UTF-8 are an error pointing to `download`; a multi-byte character cut by the range ends is left out, and the header says what was returned. `write_file` with `overwrite: false` on an existing path is an error; it writes like a remote edit (temporary file and rename over SFTP, in place over FTP).
11. **Errors.** `SITE_UNAVAILABLE` for an unknown site and for "No access" (one text); `READ_ONLY` names the site and that the user must allow more; `SSH_ONLY`; `PROTECTED` names the path; `UNREACHABLE`, `TURNED_OFF`, `VERSION_MISMATCH` come from the relay; a failed file operation is `<what failed>: <the error's English message>` (remote-side errors carry only what the agent asked about).
12. **Connection failures are fixed sentences** per `ErrorKind` (`Auth`: the user must fix the site's credentials in hoprs; `HostKey` with `hoprs_ssh::host_key_change`: `HOST_KEY_CHANGED`; other `HostKey` / `Tls`: refused in the hoprs window; `Network`: could not connect to `<host>:<port>`; anything else: could not connect), never the error's own text: an authentication error may name a key file.
13. **Sessions.** A session started by an agent call is `agent_only` until a tab connects the same site (then it is the tab's and the agent service never closes it). A tab closing its session closes it for the agent too (the next call connects again). The service closes an `agent_only` session after a failed or timed-out connect, when its site is no longer open to agents, and after 10 idle minutes, but never while the site has an unfinished transfer (closing pauses the site's queue). The reaper runs for the whole run, whatever the switch says.
14. **Prompts.** The dialogs of a session an agent started carry `by_agent`. After 120 s without a connection the service closes the `agent_only` session (which withdraws its dialogs) and answers `WAITING_FOR_USER` if a dialog was open, else a connect time-out. A session a tab also uses is left alone: only the wait ends.
15. **Windows local paths.** The local side is `LocalFs::new("/")`: it reaches the current drive only. A local path on another drive, a UNC path and a relative path are tool errors that say so.
16. **Protected roots:** `<base>/hoprs` for each of `dirs::config_dir`, `data_dir`, `cache_dir`, `runtime_dir` and `std::env::temp_dir()`; the backend's own `profile_dir`, the queue's directory, `edit_dir`, `recovered_dir` and the channel's directory; `<home>/.ssh`; the `known_hosts` file in use; every `ssh.key_file` of a saved site, read from the vault at each check.
17. **The switch:** `settings.toml` key `agents_enabled` (written only when `true`). The backend holds it in a `tokio::sync::watch` so the server follows it without the UI. The Settings section sits between Terminal and Backup, icon `Icon::PlugsConnected`.
18. **The level in the form:** three `theme::segment` buttons and one hint line under them for the chosen level (none for "No access").
19. **The log:** target `agent`, level INFO, one line per call: `read /var/www/app/config.php on "Acme produção"`, ``ran `systemctl status nginx` on "Acme staging" (exit 0)``, `read /etc/shadow on "Acme" (failed: Permission denied)`, `refused write_file: site not available`. Control characters in a path or command become spaces, so one call is one line.
20. **An unknown `agent_access` value** in `sites.toml` (a newer hoprs) reads as "No access", not as an unreadable site.
21. **The landing page has no feature list;** the site gains one FAQ entry in both languages and the privacy line.
